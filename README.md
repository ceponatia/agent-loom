# agent-loom

Weave one set of role definitions into native agent files for both [Claude Code](https://code.claude.com) and [Codex](https://developers.openai.com/codex). You write role instructions and routing once, in a small set of plain-text/JSON sources, and a single script renders them into the `.claude/agents/*.md` and `.codex/agents/*.toml` files each tool actually reads — kept byte-for-byte in sync, with drift detection so a hand-edit to a generated file can never silently diverge from its source.

The catalog shipped in this repo (namespace `example`) is a **worked example**, not a fixed product: a 12-role GitHub-issue → implementation → review → PR workflow. Treat it as a starting point to copy and reshape for your own project's roles, routing, and policy.

## Requirements

- **Python 3.11+** (the generator uses the standard-library `tomllib`, added in 3.11 — no third-party dependencies, nothing to `pip install`).
- Claude Code and/or Codex CLI, installed separately, if you want to actually run the generated agents.

## Repository layout

```
.agents/                   canonical sources — edit these
  catalog.json              role registry: names, descriptions, model/effort routing, tool grants
  common.md                 shared preamble prepended to every role's instructions
  policy.json               project policy (concurrency, retries, merge gates) — informational, not enforced by the generator
  roles/<role>.md            per-role instructions
  skills/<skill>/SKILL.md    portable skill definitions, referenced by role and mirrored to Claude
  references/*.md            supporting docs (routing/budgets, PR lifecycle, handoff contract, etc.)
  AGENTS.md, CLAUDE.md        root instructions for Codex/Claude when working in this repo
  generated-manifest.json     checksums of the last generated output — written by the script, do not hand-edit

.claude/agents/<name>.md    generated — Claude Code native subagent definitions
.claude/skills/<skill>/      generated — mirror of .agents/skills, in Claude's expected location
.codex/agents/<name>.toml   generated — Codex native subagent definitions

scripts/
  sync_agents.py             the generator
  tests/test_sync_agents.py  its test suite
```

Everything under `.claude/` and `.codex/` is generated output. Files there open with a `Generated by scripts/sync_agents.py; edit canonical .agents sources.` marker — never hand-edit them; edit the matching file under `.agents/` and regenerate instead. The generator refuses to overwrite a generated file that was hand-edited out of band (its hash no longer matches the last manifest), so a stray edit is a loud error, not silent data loss.

## Defining your own agents

1. **Roles** live in `.agents/roles/<role>.md` — the role-specific instructions, kept short (this kit's roles run 5–10 lines). `.agents/common.md` is prepended to every role automatically, so put cross-cutting rules there once instead of repeating them.
2. **Skills** live in `.agents/skills/<skill>/SKILL.md` — the portable, longer-form playbook a role loads on demand (referenced from the role's generated file as its primary workflow, and mirrored verbatim into `.claude/skills/`). One skill can be shared by more than one role.
3. **`catalog.json`** wires it together. Each entry in `roles` needs:
   - `id` — internal identifier (used by tests/tooling, not rendered)
   - `name` — the rendered agent's name; must be lowercase-kebab-case and match `^[a-z][a-z0-9-]*$`
   - `description` — shown to the orchestrating model when it picks which agent to delegate to; make it discriminative
   - `source` — path to the role's `.md` file under `.agents/roles/`
   - `skill` — the skill directory name this role preloads (must exist under `.agents/skills/`)
   - `codex` — `model`, `model_reasoning_effort`, `sandbox_mode`
   - `claude` — `model`, `effort` (omit/`null` for models without an effort control, e.g. Haiku), `maxTurns`, `tools`, `permissionMode`, `isolation` (`"worktree"` or `null`)
   - `activation` — free-text note on how the role gets invoked (not read by the generator; documentation for humans)
4. **`policy.json`** holds project-level policy (concurrency limits, retry/escalation thresholds, merge gates, root-human-decision categories). It is **not** read by `sync_agents.py` — it's a convention your roles' instructions can point to, and a real orchestrator/controller would need to enforce it itself.
5. To add a role: write its `roles/<name>.md`, add or reuse a skill, add its entry to `catalog.json`, then regenerate (below). To remove one: delete its `catalog.json` entry and its role file; the generator prunes the now-stale `.claude`/`.codex` output for you (again refusing if that output was hand-edited since the last generation).

Renaming the `namespace` in `catalog.json` and the `example-` prefix on role/skill names is the fastest way to make this catalog feel like it's yours rather than a fork of the sample — it's cosmetic, since the generator doesn't special-case the namespace string, but role/skill *names* do need to stay consistent between `catalog.json`, the `skill:` fields, and any cross-references inside role/skill prose (e.g. a role's instructions naming another skill by its file path).

## Running the generator

From the repository root:

```bash
python scripts/sync_agents.py
```

This reads `.agents/` and writes/updates `.codex/agents/*.toml`, `.claude/agents/*.md`, `.claude/skills/*/SKILL.md`, and `.agents/generated-manifest.json`.

Check for drift without writing anything (useful in CI, or before committing):

```bash
python scripts/sync_agents.py --check
```

Run the test suite:

```bash
python -m unittest discover -s scripts/tests -v
```

## Where to put the loom

The generator writes into `.claude/` and `.codex/` **relative to a root directory** that must already contain an `.agents/` folder — by default, that root is wherever `scripts/sync_agents.py` itself lives (two directories up from the script).

**Option A — copy the loom into your project (simplest).** Copy `.agents/` and `scripts/` into your project's root, alongside your own code, then run `python scripts/sync_agents.py` from your project root as shown above. `.claude/agents/`, `.codex/agents/`, and `.claude/skills/` land directly where Claude Code and Codex expect them for that project. This is the best default if you're not going to reuse the same catalog across multiple projects.

**Option B — keep the loom separate, target another project with `--root`.** If you'd rather not vendor `scripts/` (and its tests) into every project, keep this repo cloned wherever you like and copy only its `.agents/` folder into your target project. Then point the generator at that project:

```bash
python /path/to/agent-loom/scripts/sync_agents.py --root /path/to/your/project
```

This reads `/path/to/your/project/.agents/` and writes `/path/to/your/project/.claude/` and `/path/to/your/project/.codex/` — nothing from agent-loom's own `scripts/` directory ends up in your project. This is the better option if you maintain one catalog (or a few variants) and apply it to several repositories, since you edit and version the catalog in one place and re-run the generator per target as it evolves.

Either way, `.agents/` has to travel with the project whose agents it defines — the generator has no built-in fetch/sync of canonical sources from elsewhere, and `--root` only relocates the read/write root, not the requirement that `<root>/.agents/` exists.
