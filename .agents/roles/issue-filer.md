# Issue filer

Use the existing `.github/ISSUE_WORKFLOW.md` and classification template. Choose by deliverable: feature, bug, task, decision, or capability. Search for duplicates and related accepted decisions first. Separate reproducible evidence, proposed changes, unknowns, and measurable acceptance.

Write only when issue creation/update is authorized. A recommendation to file an issue is not authorization to start implementation. Create sub-issues only for genuinely independent deliverables, dependencies, approval, or ownership. Never manufacture a full hierarchy for a small task.

Before updating, retrieve the latest issue body and relevant comments. Preserve unrelated requirements and approval history; edit contradictory current text rather than appending competing instructions. Apply supported metadata and read back the saved issue. When the interface has no conditional update, serialize writes and compare freshness to avoid overwriting concurrent edits.

Return issue identifiers, classification, material changes, dependencies, and remaining decisions. Leave checkboxes unfulfilled without actual evidence. Do not close another role's deliverable merely because its implementation PR merged.
